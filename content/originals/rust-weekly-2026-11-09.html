1. Actix 修复请求走私、解压耗尽与 Windows 隐藏文件泄露

本周公告覆盖五条路径：actix-http 对畸形 chunked trailer 的解析差异可形成请求走私；gzip/deflate/Brotli/Zstd 解压可在调用方限额前消耗资源；非标准大窗口 Brotli 可让约 850 字节请求触发约 1 GiB 缓冲区；actix-files 在 Windows 8.3 短文件名卷上可能通过 ENV~1 等别名暴露 .env 或 .git/config。

为什么重要：解压在 handler 与身份校验前发生，单靠提取器大小限制不能挡住；请求走私还取决于前置代理与 Actix 的解析差异，可能绕过代理/WAF 访问控制。
组件安全版本 / 条件
actix-http请求走私 >=3.20.2；通用解压 >=3.20.1；Brotli 大窗口需 >=3.20.3
actix-web>=4.18.2，并解析到安全的 actix-http
actix-filesWindows 用户升级到 >=0.7.4
升级与兼容性建议
  • 优先锁定 actix-http >=3.20.3、actix-web >=4.18.2；用 cargo tree -i actix-http 核对真实解析版本。
  • 无法立即升级时，在反向代理或 middleware 层拒绝压缩请求，或从依赖图关闭 compress-brotli；这会影响接受压缩请求的客户端兼容性。
  • Windows 静态文件服务不要把密钥、源码与站点文件放同一目录；升级后测试短文件名、chunked trailer、压缩请求和代理连接复用。

2. SurrealDB / SurrealKV 修复越界读、UAF 与双重释放

surrealkv 对短于内部键格式的输入只用 debug_assert! 检查，release 构建可发生越界读；SurrealDB 多个 KV 后端把非 'static 借用送入 affinity pool，泄露返回 future 后可 use-after-free；surrealdb-core 依赖的 reblessive 又不健全地声明 Send/Sync，安全代码可制造数据竞争与 double free。

实际影响：这些不是普通查询错误，而是内存安全边界问题。攻击面依赖本地数据、损坏/构造 SSTable、后端类型以及调用方能否泄露 future，但安全 Rust 调用方本身无需写 unsafe 就可能触发。
公告修复版本
SurrealKV 越界读surrealkv >=1.2.0；SurrealDB 4.0.0 已携带
affinitypool future UAFsurrealdb >=3.3.0
reblessive Send/Syncsurrealdb-core >=4.0.0
升级路径与风险
  • 先通过锁文件确认是否启用 kv-mem、kv-surrealkv 或 kv-rocksdb，以及实际 surrealkv 版本。
  • 4.0.0 属于主版本升级，需按官方迁移说明回归 SurrealQL、存储后端、数据格式与部署流程；仅为修复 UAF 而不能跨主版时，3.x 至少升级到 3.3.0。
  • 升级后对现有 SSTable/数据库文件做备份和只读验证，避免把损坏输入测试直接用于唯一生产副本。

3. ocipkg 加载恶意 OCI 归档可写出或删除镜像仓库之外的文件

ocipkg <=0.4.0 从归档自身的 index.json 读取镜像名，而解析器允许主机名为 ..；目标路径因此可逃逸本地镜像存储。启用 overwrite 时，代码甚至可能先对逃逸路径执行递归删除，再在外部位置解包 layer。

为什么重要：这是安装/制品导入边界上的任意文件写入与删除，公告将其归入可升级为代码执行的路径穿越。需要用户加载攻击者提供的 OCI 归档，但调用方不必已有本地权限。
升级建议
  • 升级到 ocipkg >=0.4.1；新版本同时校验 OCI reference 语法和最终路径组件。
  • 在更新前不要对不可信归档使用 overwrite；即使在容器内，也应限制文件权限与挂载范围。
  • 升级后对镜像名中 ..、绝对路径和非 normal 组件的回归样例进行验证。

4. 小型恶意 ZIP 与 Excel 文件可终止进程或耗尽内存

zip::ZipArchive::extract() 会按 symlink 条目中攻击者声明的未压缩大小预分配目标缓冲区，112 字节归档即可请求极大地址空间并触发不可捕获的进程 abort；calamine 的 CFB/OLE2 解析器则可在畸形目录流上 panic，或因自引用 DIFAT 链从 512 字节文件增长到多 GB 分配。

实际影响：上传附件、邮件处理、制品导入、备份恢复和简历/表格解析都可能直接接触不可信文件。ZIP 问题不是 Rust panic，catch_unwind 与工作线程隔离均无法挽救整个进程。
修复版本与部署建议
  • zip 升级到 >=9.0.0；这是较大版本跨度时应检查 feature、压缩算法和 API 变化。
  • calamine 升级到 >=0.38.0；影响 .xls、.xlsb 以及从 .xlsx 提取 VBA 的路径。
  • 无论升级与否，都建议把不可信文档解析放在有限内存、有限 CPU、有限时长的隔离进程中。

高危 DoSMarkdown条件触发
公告 2026-11-02

5. pulldown-cmark 再修一项 Wikilinks 二次复杂度问题

启用 Options::ENABLE_WIKILINKS 时，嵌套图片 wikilink（形如 ![[![[…]]]]）会让解析器对内部文本反复扫描，耗时随嵌套深度呈二次增长。与上周指数事件膨胀问题不同，本次事件数可很小，但解析工作仍被大量丢弃。

适用条件：仅影响解析不可信 Markdown 且启用 Wikilinks 的应用，包括使用 Options::all()；该选项默认关闭。修复已在 pulldown-cmark 0.13.6 发布。
升级与缓解
  • 从上周建议的 0.13.5 继续升级到 >=0.13.6，才能同时覆盖新披露的嵌套图片路径。
  • 无法升级时关闭 ENABLE_WIKILINKS，并限制输入长度、嵌套深度和解析时间。
  • 0.13.0 之前版本不受该特定功能路径影响；不要仅凭这一条公告判断整体安全状态。

6. rustup 1.29.3 修复旧 x86_64 CPU 与 Solaris 回归

Rustup 团队发布 1.29.3，修复 1.29.2 后在缺少 SSE4.1 的部分 x86_64 CPU 上出现的 “Illegal instruction”，以及 Solaris 的 “lock() not supported” 错误。

实际影响：如果开发机、构建节点或自托管 runner 使用较旧 x86_64 处理器，1.29.2 可能连正常更新路径都无法完成；Solaris 用户也应更新。其他平台主要是常规补丁升级。
更新方式与例外
  • 关闭可能占用 rustup 的 IDE 后运行 rustup self update；普通 rustup update 结束时也会更新 rustup。
  • 若 self-update 本身失败，官方建议下载对应 rustup-init，确认无 rustup 进程后手动替换二进制。
  • 端点防护软件可能短期拦截新二进制或大量 rust-docs 小文件；不要为绕过扫描而关闭组织安全策略，应走白名单/审核流程。

报告 2026-11-02

7. rustc 元数据稀疏编码：部分真实基准 rmeta 缩小 33%

官方 rustc-perf 周报记录：自适应稀疏编码 PR #164484 在部分真实基准上把 rmeta 体积降低 33%，并降低 max RSS；代价是相关主基准指令数平均增加约 0.4%，cycles 与 wall-time 在该报告中保持中性。团队在合并前接受了这一取舍。

为什么值得关注：大型 workspace 的元数据体积与内存占用会影响磁盘、缓存和增量构建，但这不是“编译快 33%”。数据只适用于报告涵盖的基准与比较范围，不应外推为所有项目性能。
开发者该如何使用这条信息
  • 该改动已进主分支但尚未随新的 stable Rust 发布；不要把 nightly 结果当成当前稳定工具链行为。
  • 有大型 workspace 的团队可在对应工具链发布后，记录本项目 target、rmeta、峰值 RSS 与 wall-time，再决定缓存策略。
  • 本期不把 33% 画成生态趋势图，因为它是特定 PR 在部分基准上的测量结果。

8. rustc_codegen_gcc 首次在 AArch64 上完整自举 rustc

项目进展报告称，GCC 代码生成后端已在 AArch64 上完成 rustc 全量 bootstrap，依赖 rustc 对间接返回（sret）处理的重构、禁用非请求的 linker-plugin LTO，以及后端自身的 sret ABI 实现。UI 测试通过数由 7,699 增至 7,958，失败数从 21 降至 17。

状态边界：这是替代代码生成后端的重要里程碑，不代表 stable rustc 默认支持 GCC 后端或已可替代 LLVM。报告仍列出 binutils 同步问题，并计划在完成已知修复和测试后进行 crater run。
适用人群与实践建议
  • 对非 LLVM 架构支持、GCC 优化或编译器后端开发者值得跟踪；普通应用无需更改默认工具链。
  • 项目报告中的完成度与测试数量属于该项目自报数据，不是 Rust 官方稳定性承诺。
  • 试用者应按项目构建说明在隔离环境验证，并与 LLVM 后端比较正确性、诊断和生成代码，而不是直接用于关键生产构建。

Background · 主覆盖期之前

Cargo required-targets RFC 已批准，尚待实现

RFC #4013 于 2026 年 11 月 1 日合并，早于本期主覆盖期一天，故不计入 8 条主榜。它为 Cargo.toml 的 [package] 提议 required-targets 字段，让包用 cfg 语法声明可构建目标，帮助 workspace 的包选择跳过不适用成员。

状态提醒：RFC 获批仅代表设计方向通过，不等于当前 stable Cargo 已支持；实现由 Cargo #17671 跟踪。它也不等同于限制依赖解析或 cargo vendor 的目标集合，后者被明确拆成其他设计。 RFC 原文
