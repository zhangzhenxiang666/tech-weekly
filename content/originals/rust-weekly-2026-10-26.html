1. Wasmtime 两项关键编译器漏洞触及沙箱边界

RUSTSEC-2026-0380 指出 Cranelift 位打包可能发生静默溢出与错误代码生成；RUSTSEC-2026-0379 指出 AArch64 后端在大型 Wasm br_table 上可能跳到错误目标。两项均被标为 CVSS 9.9。

为什么重要：这不是普通宿主崩溃，而是编译后代码语义可能偏离已验证的 Wasm 程序。运行不可信或多租户 Wasm 的服务，应把补丁当作隔离边界更新处理。
问题官方修复范围
位打包静默误编译>=36.0.19,<37 或 >=43.0.0
AArch64 大型 br_table>=36.0.19,<37；>=48.0.7,<49；>=49.0.4
适用条件与升级建议
  • AArch64 宿主尤其要核对第二项；位打包问题按公告版本矩阵判断。
  • 使用 Wasmtime 36、48、49 维护线时采用对应补丁版；准备进入 50 的项目仍需完成破坏性升级测试。
  • 升级后重新编译缓存中的模块/组件，避免继续运行由旧编译器产出的代码；具体缓存策略按应用配置核验。

2. Rust TLS 信任链修补，rustup 1.29.2 同步发布

RustSec 披露部分 webpki-roots、webpki-root-certs 与 rustls-webpki 版本可能接受包含已失信 emSign 中间公钥的证书路径。Rustup 1.29.2 仅更新相关依赖以处理 CVE-2026-111943。

实际影响：仅更新 rustup 不能替代应用依赖升级。任何直接或传递使用 rustls/webpki 信任存储的服务都应检查锁文件；兼容包 0.26.11 本身不含独立根列表，真正决定安全状态的是解析到的 1.x 父依赖。
版本与操作建议
  • webpki-roots / webpki-root-certs：解析到 >=1.0.10。
  • rustls-webpki：使用 >=0.103.16,<0.104.0-alpha.1，或 >=0.104.0-alpha.8。
  • 更新 rustup：关闭可能占用它的 IDE 后运行 rustup self update；正常 rustup update 结束时也会自动更新。

3. Tokio 1.54.0 发布后由 1.54.1 回退定时器变更

Tokio 1.54.0 将 MSRV 提升至 Rust 1.85，新增 worker_index()、运行时繁忙周期 I/O 上限、同步原语与文件时间 API，并支持 Emscripten JSPI。10 月 21 日的 1.54.1 回退了“从定时器移除运行时句柄”的改动。

实际影响：这是后端项目最直接的升级项。若你的 workspace 仍承诺低于 Rust 1.85，不能无条件解析到 1.54；计划升级者应直接测试 1.54.1，而不是停留在 1.54.0。
兼容性检查
  • 核对 CI、容器与下游库声明的 MSRV；对库作者而言，这可能是对使用旧编译器用户的破坏性变化。
  • 重跑暂停时间、定时器、嵌套运行时与阻塞任务测试。
  • 零容量缓冲等部分非法配置现在会 panic 或被拒绝，应检查动态配置入口。

4. Wasmtime 50.0.0 发布：组件异步语义与 WASIp0 默认值变化

Wasmtime 50 增加默认关闭的 compact imports、组件 canonical names/accessors、空闲池内存释放 API，并让 wasmtime serve 支持继承 systemd 套接字、Unix 套接字和空闲退出。组件模型异步语义同步到新规范。

兼容性风险：CLI 不再默认启用 WASIp0（需 -Spreview0）；回调上下文、Accessor::spawn 和 component-model-async 取消语义都有 API/行为变化；从源码编译要求 Rust 1.97。
升级建议
  • 先区分“安全补丁”与“主版本迁移”：暂不能迁移 50 的项目应升级现有维护线补丁。
  • 依赖 WASIp0、Winch 非 Tier-1 proposal 或组件异步取消行为的应用需专门回归。
  • 官方未给出通用性能倍数；本期不据个别改动推导整体性能结论。

5. -Cembed-metadata 稳定化代码合并，为缩减 target 铺路

rust-lang/rust #163436 合并，将原来的 -Zembed-metadata 稳定化为可在稳定通道使用的 -Cembed-metadata。目标是让 Cargo 后续可默认使用 -Cembed-metadata=no，避免在 .rmeta 与 .rlib 中重复保存 crate 元数据。

状态边界：合并到主分支不等于当前 stable 已可用；rustc 自身仍计划默认 yes，Cargo 改默认值是后续独立步骤。现在不应在稳定 CI 中假设该行为已生效。
开发者该做什么
  • 磁盘受限的大型 workspace 可关注其进入具体 Rust 发布版的时间。
  • 不要提前把 nightly 测试数据当作所有项目的确定收益；profile、依赖图和产物类型都会影响结果。
  • 涉及直接调用 rustc、dylib 或自定义构建缓存的项目，稳定发布后仍需回归产物消费链。

6. RFC 提议严格规定 Future 请求唤醒后必须被再次 poll

RFC #4019 试图以文档契约禁止 “snoozing”：Future 若请求 wake，拥有者应再次 poll。提案同时关联给 AsyncIterator 增加 poll_progress 的 RFC，以表达不会产出 item 但仍取得进展的状态。

为什么值得关注：这是文档契约提案，却可能影响执行器、自定义 Future、流式协议和取消/背压模式的正确性判断。它尚未合并，当前不是稳定语义变更。
当前建议
  • 维护自定义 Future/执行器的团队可审计 wake 与 poll 的配对假设，但不要按未通过 RFC 重写公共 API。
  • 关注与 poll_progress 的协同讨论，尤其是 AsyncIterator 和无 item 进展场景。
  • 普通 Tokio 应用暂时无需采取升级动作。

7. Cargo 合并新的 build-std 配置键，但行为仍待后续实现

Cargo #17602 加入 build.build-std.when 与 build.build-std.crates 配置键，作为 build-std=always 路线的一部分；PR 明确说明这些键目前还不执行行为，后续补丁会以不稳定 -Z 开关保护。

实际影响：这是配置界面和迁移路径的基础设施，不是稳定 Cargo 功能。目标是未来替代现有 -Zbuild-std 流程，但当前项目不能删除原有 nightly 配置。
使用边界
  • 仍按当前工具链的 -Zbuild-std 文档操作。
  • 嵌入式、自定义 target 与自建标准库用户可开始评估未来配置形态。
  • 不要把配置键能被解析等同于标准库已按条件构建。

8. Rust 编译器团队设立 GPU 通知组与 Linker 工作区

编译器团队宣布两个新协作组：GPU target notification group 汇集 AMD、Nvidia、Intel 等厂商专家协助诊断 GPU 目标问题；Linker Working Area 聚焦替代链接器集成，并作为链接器问题的联络点。

为什么重要：这不是新语法或即时工具链功能，而是明确了 GPU 后端和链接器集成的维护责任与沟通入口。对自定义 target、GPU 计算和替代链接器贡献者尤其有价值。
范围说明
  • 替代链接器（官方举例 Wild）仍需具体实现与评审，组织成立不代表已默认集成。
  • 普通应用无需改配置；遇到相关 rustc 问题时可使用对应 Zulip 流与团队渠道。

9. RFC 提议弃用 std::env::args 与 vars

RFC #4021 提议弃用 Unicode 字符串版本的进程参数与环境变量迭代器，鼓励改用 args_os 和 vars_os，以免隐藏无效 Unicode 的错误处理并导致 panic。

状态边界：RFC 仍处于开放讨论，标准库 API 没有在本周被弃用。若提案最终通过，依赖字符串版本的 CLI 和服务可能逐步收到弃用警告，但迁移需要显式决定非 Unicode 数据如何处理。
提前审计建议
  • 边界层保留 OsString，在业务层按场景选择严格转换或有损转换。
  • 不要机械替换后立即 unwrap，否则只是把错误位置移动。
  • 库作者可先梳理公开 API 是否错误地假设环境与参数总是 Unicode。
