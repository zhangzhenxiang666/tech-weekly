1. Cargo Nextest 可移植录制重放存在任意代码执行

RUSTSEC-2026-0412 指出，cargo-nextest 0.9.125–0.9.149 在 cargo nextest run --rerun 读取恶意可移植录制时，会把未校验的构建作用域参数传给 Cargo；攻击者可注入 --config，进而配置编译器包装器、链接器或依赖源并执行代码。

为什么重要：代码在测试真正开始前、构建阶段就能以调用者权限运行；CI 中可能接触仓库令牌和部署凭据。预先执行 cargo nextest replay 也不能规避，因为构建已先发生。
适用条件与升级建议
  • 仅影响启用实验性 run recording 的用户，例如设置 NEXTEST_EXPERIMENTAL_RECORD=1，并重放攻击者提供的录制。
  • 升级到 cargo-nextest >=0.9.150；可在 .config/nextest.toml 设置 nextest-version = "0.9.150" 提醒协作者。
  • 无法升级时不要启用实验录制，也不要重放不可信录制或直接从网络管道输入；工具升级后重跑 CI 行为兼容性测试。

2. Pingora 修复 HTTP/2 主机边界、内存耗尽与代理头绕过

本周三项 RustSec 公告覆盖：HTTP/2 :authority 与 Host 不一致可导致缓存投毒或主机访问控制绕过；默认头列表与并发流限制可被远程耗尽内存；向 HTTP/1 上游转发客户端指定的 Connection/hop-by-hop 头，在特定链式代理中可能绕过 ACL。

实际影响：自建网关、反向代理与缓存服务若直接接收不可信 HTTP/2 或链到其他 HTTP/1 代理，应把它视为边界修复。Cloudflare 公告说明其 CDN 客户不受所述内部部署路径影响，但这不等于所有 Pingora 用户都安全。
公告修复版本 / 条件
0388 · Host 与 :authoritypingora-core >=0.9.0
0389 · HTTP/2 内存耗尽pingora-core >=0.8.1；自定义 H2Options 仍须显式限额
0390 · Connection 头绕过pingora-proxy >=0.9.0
兼容性与部署建议
  • 优先升级至 0.9.0 及以上并回归 Host 规范化、缓存键、上游路由与 400 响应。
  • 若应用传入自定义 H2Options，修复后的默认值不会自动覆盖；需显式设置 max_header_list_size 和 max_concurrent_streams。
  • 不要用 HttpUpstreamRequestPolicy::preserve() 恢复旧行为，除非能证明源站不依赖代理添加的安全头。

3. Juniper 系列修复无需认证即可触发的资源耗尽

juniper 的深层嵌套文档可触发栈溢出，构造的 fragment/字段组合可造成超线性 CPU 与内存消耗；juniper_hyper 与 juniper_warp 还会无上限读取 POST 请求体。四项公告的 CVSS 均为 7.5。

为什么重要：单个未认证请求就可能终止进程或显著耗尽资源。修复不仅换算法，还引入默认深度、token、字段和 2 MiB 请求体限制，因此升级后可能拒绝过去被接受的超大查询。
包安全版本与新默认
juniper>=0.17.2；深度 64、token 15,000、展开字段 15,000 等上限
juniper_hyper>=0.10.1；默认请求体 2 MiB
juniper_warp>=0.9.1；默认请求体 2 MiB
升级与兼容性建议
  • 直接暴露 GraphQL 端点的服务应优先升级，并用真实最大查询与批量请求做回归。
  • 确需更高限制时，使用 RootNode::limit_depth/limit_tokens/limit_fields 或相应 body-limit API；不要简单取消限制。
  • 在网关层继续保留请求体、超时与并发配额；库内限制不能替代整体资源治理。

4. 两个发布归档工具出现目录穿越：一个已修、一个无补丁

nix-nar::Decoder::unpack 可被恶意 NAR 通过符号链接与路径组合写出目标目录；sn-releases::extract_release_archive 对 ZIP 条目名缺少穿越检查，可发生 zip-slip 与任意文件写入。

实际影响：解包通常位于安装器、更新器或发布流水线，具备较高文件权限。nix-nar 已在 0.6.0 修复；sn-releases <=0.3.1 截至公告时没有修复版本，且项目被标为不再维护。
处理建议
  • nix-nar 升级到 >=0.6.0，并用含符号链接与 .. 的测试档回归。
  • 使用 sn-releases 时停止解包不可信归档；迁移到维护中的替代实现，或在独立低权限沙箱中完成并验证所有目标路径。
  • 无修复版本意味着不能把单纯重新锁定到 0.3.1 当成缓解措施。

5. Wasmtime 50.0.1 修复 WASI 权限与组件模型边界问题

50.0.1 集中修复五项：WASIp3 UDP 发送权限检查、WASI HTTP p2 的 Content-Length 与正文不匹配、跨 Engine 的宿主创建 GC struct 类型混淆、i31/nullref typed function 参数检查不足导致 panic，以及跨组件实例转移 borrowed resource 时未通过 ResourceLimiter 记账。

为什么重要：影响从协议完整性、权限边界到宿主内存控制，尤其值得运行不可信组件、启用 WASIp3/WASI HTTP 或使用 WasmGC 的服务检查。RustSec 给出的严重度并不相同，应按功能暴露面而不是只看一个总分判断。
维护线包含相应补丁的版本
50.x>=50.0.1
49.x>=49.0.5,<50
48.x>=48.0.8,<49
36.x LTS部分公告要求 >=36.0.20,<37
升级建议与边界
  • 留在 36/48/49 的项目按各公告的 patched 区间核对，不要仅看到 50.0.1 就误以为必须跨主版本。
  • 升级后重测 socket 地址策略、HTTP framing、跨 Engine 类型与 component resource limiter；这些路径并非所有应用都会触发。
  • 50.0.1 是 50.0.0 的补丁版；若仍从 49 或更早迁移 50，上一期列出的主版本 API/行为变化仍需单独验证。

6. Orion 修复 LLVM 引入的时序泄漏与 BLAKE2b 状态错误

RUSTSEC-2026-0426 指出，LLVM 在部分目标上把本应常数时间的条件减法编译为依赖秘密数据的条件跳转，影响 ML-KEM 与 ML-DSA；RUSTSEC-2026-0428 则指出用不同长度密钥调用 Blake2b::reset() 会产生错误 tag。

实际影响：第一项可能泄露密钥，已观察到 i586、s390x，部分 ML-DSA 路径也涉及 x86_64；第二项在诚实协议参与方之间也会导致验证失败。两项均在 0.17.16 与 0.18.1 修复。
适用条件与升级建议
  • 使用 orion ML-KEM/ML-DSA 或 hazardous BLAKE2b API 的项目升级到 ^0.17.16 或 >=0.18.1。
  • 时序问题的可利用性依赖编译器、CPU 和攻击者与进程的距离；不能因目标平台未在已观察列表中就假设安全。
  • 密码学补丁升级后应重跑协议互操作、已存测试向量与跨平台构建。

7. rustls-ffi 客户端构造器修复 server_name 生命周期错误

rustls-ffi 0.12.0–0.15.6 的两个客户端连接构造器在返回后仍保留调用方 server_name 缓冲区引用；文档又未要求该缓冲区长期存活，因此临时字符串被释放或复用后会发生 use-after-free。

实际影响：最可能受影响的是把临时字符串传入 C API 的其他语言绑定。0.15.7 改为复制输入；若调用方让 server_name 在整个配置生命周期存活，则公告说明不受影响。
升级建议
  • 升级到 rustls-ffi >=0.15.7，并重建依赖它的本地库与语言绑定。
  • 无法立即升级时，确保 server_name 存储在连接/配置完整生命周期内不被释放、移动或复用。
  • 升级后重点测试临时字符串、异步连接创建和多语言 FFI 封装。

8. pulldown-cmark 的 Wikilinks 可触发指数级事件膨胀

启用 Options::ENABLE_WIKILINKS 时，带空显示文本的链接（如 [[a|]]）会让后续解析事件近似倍增。公告给出的复现中，112 字节输入产生 327,676 个事件，足以让收集事件或渲染 HTML 的服务耗尽内存。

适用条件：Wikilinks 默认关闭；只有解析不可信 Markdown 且显式启用该选项（包括通过 Options::all()）的应用受影响。修复已在 pulldown-cmark 0.13.5 发布。
升级与缓解
  • 受影响项目升级到 >=0.13.5；0.13.0 之前版本不受该特定问题影响。
  • 不能升级时关闭 ENABLE_WIKILINKS，并在服务层保留输入长度、输出事件数和渲染时间限制。
  • 升级会改变恶意/边界输入的事件序列，应对依赖 Wikilinks 的渲染器做快照测试。

9. Inside Rust 公布可变参数泛型微型调研结果

调研收到超过 3,300 份提交，并人工整理开放回答。受访者常见需求包括为任意长度 tuple 实现 trait、替代重复宏、解析器组合子、SQL 列/参数、张量维度与结构体字段映射；整体结论被概括为“谨慎但感兴趣”。

状态边界：这是语言设计输入，不是已接受 RFC、nightly 功能或稳定化计划。它说明宏和固定 tuple 长度带来的真实成本，也同时记录了对语言复杂度的担忧。
开发者如何解读
  • 库作者可用报告中的用例帮助未来提案证明收益，但当前仍需使用宏、tuple 上限或动态分发等既有方案。
  • SQLx、Bevy 等被回答者作为具体用例提及，不代表这些项目已承诺迁移或实现。
  • 未来方案需要同时展示清晰可读的语法与相对宏方案的显著优势；不要据此承诺版本时间表。
